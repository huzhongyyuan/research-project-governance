# 评测与 baseline 公平性

结论最常见的失效点往往不在方法，而在评测管线。正式评测（进入论文、或决定资源投入的对比）在运行前按本清单写入协议卡（protocol 模板的"公平性检查"一节），审查者逐项核对后才出数字。适用于模型、算法、系统等各类对比实验。

## 运行前

1. **打分器冻结**：所有方法共用同一份打分代码、同一版本、同一参数，不为新方法改打分器。复制打分脚本时，确认其根路径和输出目录都指向新目录。
2. **成员一致**：同一样例列表，同一数据格式（长度、尺寸、单位、色彩或编码空间）。缺失样例记为失败，留在分母里。
3. **输入输出链路等价**：写出每个方法从原始输入到被打分文件的完整链路，包括预处理、缩放、量化或编码、传输、解码、后处理、封装。无法消除的差异（例如某方法的接口只能传有损格式）要披露，并用对照组量化。
4. **对照组**：
   - `input_noop`：把原输入原样当作预测，给出"什么都不做"时的指标水平；
   - `transform_control`：原输入走一遍被测方法的完整链路，但不经过方法本身。二者之差就是链路自身的偏差，单独报告，不混进方法差距。
5. **条件输入冻结**：自动生成的提示词、指令、标注、超参数，在看到任何方法输出之前生成一次并冻结，只用输入和允许的标注，不用答案或 GT。生成出错计为该方法失败，不事后修改、不删例。用了辅助信息（例如借助标注写文字指令）要注明。
6. **补充组单列**：给 baseline 额外信息的变体（例如额外给定区域或标签）单独命名，并标注"使用了 X 信息"，不和主结果混在一张表里。
7. **输出隔离**：结果只写进本次评测的目录，不覆盖任何已有汇总。每个输出目录放一份来源记录：方法、版本、协议、条件来源。

## 运行中

- 失败即停：任何一例在生成、转换或打分中出错，流程就失败退出，不静默跳过。复用已完成的例子时，同样先校验它是否完整。
- 汇总前检查解析失败、超时这类异常列表为空。

## 运行后

1. **逐例完整性**：每个指标来源都逐例核对状态和错误字段，不只数文件个数。
2. **配对统计**：对同一样例算方法间差值，给 bootstrap 95% 置信区间，再报"更差的例子数 / 总数"。区分整体指标和关键区域指标：整体指标会被"保留大部分原输入"一类的做法天然抬高。
3. **看样例**：抽查成功、典型失败和极端例子的原始输出，确认数字和实际结果一致。失败样例要进入汇报。
4. **汇报**：主结果、对照组偏差、补充组、已知限制（条件生成错误、链路限制）分开写。

## 受控诊断实验

回答"某个因素是否导致失败"时，构造只改变这一个因素的配对输入：同一样本、同一条件，只改位置、尺度、顺序、视角之类的单一变量。

- 优先用无损变换，例如平移、置换、循环移位。
- 有损变换（重采样、插值）要加同变换对照，并写明它引入的混杂因素。
- 报告配对差值，不只报各组绝对值。
